# Incident — instance wedged (OOM), missed ride notification

- **Date:** 2026-08-20
- **Severity:** low (single-user system; no data loss)
- **Status:** resolved
- **Author:** Nick

## Summary

The AWS Lightsail instance (512 MB, us-east-2) running the cycling-agent cron job
and the Discord approver bot became unresponsive after running out of memory. The
`sync` cron job could not run, so a ride that had just finished was not analyzed
or emailed on schedule. A reboot recovered the instance; the ride was then
analyzed and delivered automatically, with no data lost. A 2 GB swapfile was added
to prevent recurrence.

## Impact

- One ride-analysis email was delayed (delivered on recovery, not lost).
- The instance was unreachable (including browser SSH) for the duration of the
  wedge until a reboot.
- No data loss; no corrupted state files.

## Detection

Detected by **absence of the expected notification** — the ride-analysis email
that normally arrives shortly after a ride never came. Attempting to open the
Lightsail browser SSH terminal returned `UPSTREAM_ERROR [515]`, indicating the
instance's SSH daemon was unresponsive (the box was wedged, not merely a bad
network path).

## Timeline (UTC, approximate)

- **~ride time** — ride finished and synced to Strava; the next cron run was
  expected to analyze and email it.
- **before recovery** — instance unresponsive; browser SSH failed with
  `UPSTREAM_ERROR [515]`. No analysis ran; no email sent.
- **2026-08-20 23:13** — instance rebooted (Stop → Start from the Lightsail
  console, out-of-band). systemd auto-started the Discord bot on boot; cron
  resumed.
- **shortly after** — the pending ride (still unsynced) was picked up by cron,
  analyzed, and the email delivered.
- **2026-08-20 23:13+** — root cause confirmed and prevention applied (see below).

## Root cause

**Out-of-memory on an under-provisioned instance with no swap.**

At idle the 512 MB box had ~156 MB available with only the ~41 MB Discord bot
running, and **no swap configured** (`Swap: 0B`). A `sync` cron process
(Python + the Anthropic SDK + `requests` + loading the plan/history into memory)
spikes memory by an additional ~100–200 MB. With no swap to absorb the spike, the
Linux OOM killer terminated a process, and the instance was left wedged and
unreachable.

## Resolution

- **Mitigation:** Stop → Start the instance from the Lightsail console
  (out-of-band, since SSH was down). On boot, systemd restarted the bot
  (`Restart=always`, enabled) and cron resumed.
- **Recovery of the missed work:** none needed manually — the ride had never been
  marked "synced" (the wedged box never processed it), so the next cron run
  correctly treated it as new and delivered it.

## Why no data was lost

Two prior design choices did their job:

1. **Idempotency / mark-synced-after-processing** — activities are only recorded as
   synced once analyzed, so an interrupted run leaves work to be safely retried
   rather than silently dropped.
2. **Atomic state-file writes** — `storage.write_json_atomic` means an OOM kill
   mid-write cannot corrupt `recent_activities.json`, the adjustments ledger, or
   the Strava tokens.

## Prevention / action items

- [x] Add a 2 GB swapfile so memory spikes spill to disk instead of triggering the
  OOM killer.
- [x] Persist swap across reboots via `/etc/fstab`.
- [ ] If OOM recurs even with swap, upgrade to the 1 GB Lightsail tier.
- [ ] (Optional) lightweight memory monitoring / alert, so pressure is visible
  before it becomes an outage.
- [ ] Adjacent gap noticed while triaging (separate from this incident): `sync`
  marks an activity synced *before* it emails, so a delivery failure would lose the
  notification (the analysis is still saved to `output/`). Consider marking synced
  only after successful delivery, or a small delivery retry/queue.

## Lessons

- On a small VM, **swap is not optional** once you add a persistent process
  alongside batch jobs that spike memory.
- **Absence of an expected signal is a valid alert.** The missing email was the
  first indication of the outage — worth having explicit heartbeat/failure
  alerting so silence isn't the only signal.
- Recoverability came from boring, defensive choices (idempotency, atomic writes)
  made before they were needed — which is exactly when they pay off.
